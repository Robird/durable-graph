# 类型头方案盲评：共同需求与评价合同

这是候选架构研究材料，不是实施合同。两份候选不透露提出者、实现状态或迁移成本；评审按从零设计比较。

## 1. 共同需求

以下产品约束来自本次研究的需求方；并非由某个候选方案推导。

1. 产品是带 Schema 历史的对象图增量序列化库。领域对象有方法和 transient 状态；持久化先捕获冻结状态 DTO，再编码。恢复先读回落盘版本 DTO，再显式 Upgrade，最后恢复领域图。
2. 所有受支持引用对象共用 ObjectId 空间，包括用户 class、string、数组，以及后续受支持的 BCL 内容对象。共享和循环引用需保留；空 string 可统一为 Empty。ObjectId 为不携带目标泛型参数的整数语义包装，0 为 null。
3. 引用对象在自己的 Base 中记录自身表示所需的类型/版本信息；Delta 沿用该 Base 的解释。引用目标独立升级不应仅因版本改变就强制改写所有引用者。
4. struct 作为字段/数组元素内嵌，无独立 ObjectId。内嵌值或基类的 exact 布局必须可追溯；变化不能偷偷重解释原有 bytes。owner 的业务 Upgrade 显式决定转换；引用对象跨布局续写用新 Base。
5. 支持用户泛型 class/struct、基元、string、SZ 数组及零下界 rank 2–4 数组，允许这些支持项递归组合。无 boxed value、接口/object 通配槽、数组协变；BCL 以后按内容合同接入。
6. Schema 历史和可执行历史 reader 都显式保留。读取历史 DTO 不应要求旧领域 CLR 类型仍存在，不允许用 current/latest 补缺；元数据不等于可执行 reader。
7. 仓库内已持久注册的身份不能重绑定为另一份含义；冲突拒绝。原型阶段单 writer、Schema 注册单调积累；允许 Schema 注册成功而后续 State 未发布。若引入本地整数编号，它不得仅保存在进程内；重开后需稳定。跨仓库编号相同不要求意义相同。
8. 追求实现简单、可维护、紧凑编码和有效解码。不要求这轮产生可执行迁移、不要求保留未发布旧格式、不预建分布式注册、GC 或联合 Store 事务。

## 2. 必须分别评价的选择

- 仓库本地整数 token，还是每个对象重复逻辑类型描述。
- SchemaStore 登记版本化开放模板，还是闭合 exact 布局，或二者有分工。
- postfix/stack 还是 prefix/recursive 编码：两者须在相同 token 编码、终止条件和缓存条件下比较。
- nominal 领域身份、版本化值布局、生成 DTO CLR 类型之间怎样映射；不假定 DTO CLR 类型本身能唯一反推 nominal 身份。
- 统一对象头描述还是按种类分支描述；语义是否必须与表面格式一样统一。

## 3. 共同案例

用示意名称即可，不查任何现有源码或项目文件来推断实现。

1. 非泛型 `Node` v1/v2，`Node.Next` 自环；子对象升级而引用者内容不变。
2. `Point` 是 inline struct，v1 `{int X}` → v2 `{long X, int Y}`；比较 `Point[]`、`Point[][]` 与 `Box<Point>`（`Box<T> { T Value; }`）。
3. `Pair<A,B> { A First; B Second; }`，测试 `Pair<int,Point[]>`、`Pair<Point,string>`、`Pair<Node,string>`。
4. `Carrier<T> { Point Fixed; T Value; }`；Point 改版如何影响 Carrier 模板与不同闭合？再测试不使用 T 的 `Marker<T>`，及 `Node`/`string` 都投影为 ObjectId 的参数。
5. 空数组、泛型基类、读回不保留旧领域 CLR 声明的历史 DTO。
6. 两次进程重开注册顺序不同；先注册元数据再保存失败；未知/错误 arity token、截断表达式应明确失败。

## 4. 输出合同与证据边界

独立给出推荐，允许条件推荐、合并或两个候选都不满足；不要为了平衡而平局，也不要假设某个已经实现。

- 先说明两案共同的不可省语义，再分别列最强优点和最强反例。
- 给上述案例中的至少一个完整符号化写入/读取过程；指出方案材料尚未定义的步骤，不替它默默补全。
- 至少给一组公平的 token/字节计数例子；必须声明编号范围、varint、字符串长度、结束/长度标记等假设。不能把整数寻址的收益归因于 postfix。
- 区分“可以用该机制解决”“材料已完整定义”“有可执行证据”。没有基准时不要宣称一定更快。
- 对主要建议写明：对应材料位置、需求依据、复杂性代价、最小改进、删除该语义的具体失败、信心及未知项。
- 不按投票裁决，不查项目实现、其他设计文档、其他 reviewer 结果或外网。这里只比较材料内架构，运行性能与工程落地仍是待验证结论。

本文和候选均由同一主持人整理，不是三份独立证据。首轮 reviewer 相互隔离，顺序对照只能帮助发现锚定，不能证明消除模型与材料偏差。
