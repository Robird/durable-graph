# 候选 A

## 1. 元数据与身份

SchemaStore 为每个版本化用户 Schema **开放模板**分配仓库内稳定整数 token。非泛型是零参数模板。
记录包含逻辑定义身份、版本、泛型形参数量、成员与基类定义，以及模板自身需要锁定的历史依赖。
逻辑名称和版本存于注册表；对象头使用整数，不逐对象重复名称和版本。
整数本身只在所属仓库目录中有意义；同一注册身份不得对应冲突定义。

开放模板连同有序实参构成闭合表示描述。模板作为领域类型与对应冻结 DTO、历史 reader、投影/恢复能力的关联中心；
整数记录并不意味着 DLL 中一定存在相应 reader，执行能力仍须显式保留和绑定。

## 2. 对象头

用统一的二进制 postfix 表达式表示受支持类型组合。基元为内建短 token；数组构造为消费一个操作数的内建操作；
用户泛型模板 token 消费已知 arity 个类型操作数。按模板版本从 SchemaStore 得到 arity 和解释。

符号例子（表示表达式语法，不等于已经确定其 DTO 投影细节）：

```text
int Point_v2 SZ Pair_v1
    => Apply(Pair_v1, [int, Array(Point_v2)])

Point_v2 SZ Rank2
    => ArrayRank2(Array(Point_v2))
```

解码从 token 序列构造闭合描述，再据此绑定对应 DTO 表示与 reader；不直接依赖当前领域 Type 的反射布局。
Type header 后跟该对象的 Base body；Delta 继承 Base 解释。
表达式整体的长度/结束方式、用户 token 与内建码区间的划分尚需确定；须计入空间成本。

## 3. 值、引用和泛型

字段或元素为 struct 时内嵌其冻结状态；为引用时投影成 ObjectId，目标对象类型/版本在目标自己的头中。
上面的闭合描述必须能同时提供领域 nominal 身份和本对象实际值布局；不能因为类型表达式组合就把独立引用对象内联进 owner DTO。

例如领域 `Pair<int, Point[]>` 的第二个字段仍是 ObjectId，Point 数组作为另一个对象存储。
`Pair<Point,string>` 的第一个字段内嵌 Point 历史 DTO，第二个字段是 ObjectId。
引用目标独立升级不应使未改内容的 Pair 必须跟着升级/重写。

待明确：闭合参数中哪些位置记录 exact 版本、哪些只表达引用的 nominal 约束；
不同参数槽角色如何从模板推导；phantom 参数及多个领域引用类型投影成同一 ObjectId 时如何保留身份；
模板中的固定 inline/base 历史依赖如何与实参代入共同决定完整布局。
这些问题可由模板/闭合算法承担，但本材料未把该算法写成正式合同。

## 4. 读写路径

写入：捕获领域图及冻结 DTO → 确认所需版本化模板已持久登记并取得 token → 组合该对象表示表达式 → 写 Base/Delta。
读取：解析表达式并查询模板 → 构造闭合历史描述 → 绑定历史 reader → 解码 DTO → 独立执行 Upgrade → 恢复领域图。
闭合描述/reader 可缓存，缓存键必须包含全部必要历史依赖。元数据登记应在引用它的 State 发布前持久。

## 5. 需要评价的成本与收益

预期收益是对象头紧凑、统一表达式组合和整数目录查询；开放模板可被多个闭合复用。
成本包括稳定 token 登记/恢复、模板参数代入与两个类型表示间的映射、严格表达式校验。
同版本模板/闭合的完整一致性、缓存身份、内建 codec 的版本解释仍需有清晰规则。
编码短和解码快是应测假设；本材料不以 postfix 本身作为性能证明，也不预设需要另一份闭合持久账本。
