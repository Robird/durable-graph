# 匿名评审 v1

依据 `problem-v1.md` 与冻结的 `rubric-v1.md`，仅评审两份匿名答案的最终方案、论证和测试设计。未运行实现或测试；不按篇幅或表达风格评分。

| 答案 | 总分 | 关键语义错误 |
|---|---:|---|
| `sample-kestrel.md` | **20/20** | 未发现 |
| `sample-orchid.md` | **20/20** | 未发现 |

下表每格均为“分数；可检查证据”。

| 项目 | Kestrel | Orchid |
|---|---|---|
| R1 等价关系 | **2**；物理表使用引用相等，Key/TypeExpr 使用结构值相等；完整布局由闭包局部一致性归纳证明；最终 CLR Type 单独精确比较。 | **2**；物理遍历与按 Key 汇总分开；Shape 包含 Key、Kind、完整子布局和 closed Ref 类型；CLR Type 单独检查。 |
| R2 深层同 Key 冲突 | **2**；K 的两个物理声明分别指向含 i32/i64 的 J；`Visit` 仅对相同物理节点早退，同 Key 新节点继续下降。 | **2**；K/C/i32 与 K/C/utf8 反例；全部物理节点先生成完整 Shape，再按发现序比较同 Key 的 Shape。 |
| R3 共享深度 | **2**；L=3、浅路 R/S/T 与深路 R/A/S/T 反例；后序 height 与根上限检查覆盖所有路径。 | **2**；L=3、共享 X/leaf 的对应反例；物理 DAG 后序计算 height，各根独立检查，`longestNext` 构造见证。 |
| R4 当前 Authority | **2**；每次 `Execute` 都扫描 requirements；缺项接受，本次局部 `checked` 不跨调用保存；明确不登记、不换规则。 | **2**；每次调用重建权威规范化器并扫描要求；明确不保存 Authority 已验证事实，缺项接受。追加冲突测试检验缓存命中。 |
| R5 跨图完整比较 | **2**；`CheckRegistered` 实际遍历命中 Node 的完整闭包，与 Plan 的逐 Key 局部签名核对；不要求子 Key 独立登记。成本明确为 O(K+A+B)。 | **2**；权威闭包以共享物理 memo 完整规范化，并使用与 Plan 一致的精确 interner；桶内精确比较处理碰撞。成本计入 O(Na+Ea)，没有把深比较直接算作 O(K)。 |
| R6 依赖覆盖 | **2**；按 source/target 顺序覆盖全部步骤及零步 owner；解释递归工具端点均落在 owner exact 闭包中；Ref 只比较 nominal 类型。 | **2**；相同 owner 根集合与零步分支；明确未使用工具仍由闭包覆盖；Shape 将 Ref 保留为类型描述而不递归。 |
| R7 零回调失败 | **2**；Prepare 成功后才可入缓存；`typeof(T)` 与缓存 FinalDtoType 精确比较、深度及完整 Authority 检查均先于回调循环。 | **2**；准备期认证 Schema，执行期先检查缓存 FinalDtoType 和全部 Authority 要求，再进入回调循环；最后 cast 不承担验证职责。 |
| R8 稳定诊断 | **2**；按规定根/边顺序发现节点，有序 requirements 保存首路径；同 Key 冲突给两个路径，权威冲突带 Plan 路径；深度见证确定。 | **2**；确定性 DFS 保存 firstPath 和发现序；同 Key 的两个完整 Shape 不等时给双方路径；权威要求按首次发现序检查，冲突给 req.firstPath；深度见证固定破同值顺序。 |
| R9 共享与复杂度 | **2**；准备按物理节点处理，明确 O(N+E+R) 并补充字段扫描量 F；每次仅 K 次权威查询，不展开路径，也未增加额外治理机制。 | **2**；发现、高度、Shape 构造均按物理 DAG 共享；权威侧共用 memo，每个不同 Key 一次查询；精确结构认证是 rubric 允许的替代算法。复杂度表述边界见下。 |
| R10 区分性测试 | **2**；至少前五项分别检验深层双声明、共享超深、权威深层冲突、晚登记及错误 T；计数回调明确断言失败调用零回调，并另含工具、零步及规模测试。 | **2**；测试 1—5 同样覆盖上述五种具体失效场景；测试 3—5 明确回调前失败，另有等价重复与零步测试。 |

两份方案的完整布局认证依据均成立：Kestrel 检查每个物理声明的局部签名，利用完整闭包保证子 Key 的布局一致；Orchid 自底向上生成精确规范结构，直接比较完整 Shape。两者也都实际读取权威闭包，没有假定闭包中的每个 Key 必然可由 Authority 单独查得。

题目与表述边界按冻结规则从宽处理：

- Authority 的闭包自洽承诺不等于其子 Key 全部独立登记；两份答案均覆盖较弱的题设，无须补接口假设。
- 题目以不同物理节点/边 N/E 表述近线性目标，但没有将重复 owner 根出现次数 R、scalar/Ref 描述符数量 F 单列。Kestrel 明确补充了这些量；Orchid 省略了这些计数。将 Orchid 的边界补写为“计入根列表和字段扫描量、哈希索引的通常期望成本”更严谨。其算法仍按输入共享结构工作，没有指数展开；不据此临时新增扣分条件。精确桶内比较保证碰撞时的正确性，不保证任意碰撞下仍有线性最坏时间。
- 稳定诊断不要求不同正确算法在多个并存错误中选中同一个错误。两份答案各自给出了可重现的顺序和见证；Orchid 选择确定的最长路径符合 rubric，不能额外要求与 Kestrel 的首条超深路径选择完全一致。
- Orchid 额外提出输入 DTO 与绑定检查；题目没有完整规定这些接口和输入规则，因此不将其作为得分依据，也不据此推定一个未明确写出的拒绝规则。

本轮两份产物均满足冻结的 R1—R10；这一结果仅描述这两份答案在该题上的表现。
